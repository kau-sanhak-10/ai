## 실제 호출에서 발견해 보완한 내용

초기 `intake-ai05-v1`으로 14개 중 9개가 통과하고 5개는 기대 행동에 도달하지 못했다.
HTTP 200과 실제 모델 사용량만으로 성공 처리하지 않고 행동·사실·상태 검사를 실패로 남겼다.

원인 확인용으로 실패 사례 중 3개를 다시 호출해 2개 통과·1개 실패를 확인했다. 같은 표현의
응답도 달라질 수 있었다. 저장한 실제 구조화 후보에서 명시적인 수리 요청을
`REPAIR/UNCONFIRMED`로 반환한 사례와, 증상 추출값을 누락한 사례를 확인했다.
후자는 누락된 출력이며 모델 내부의 판단 이유까지 확정할 수는 없다.

프롬프트와 필드 설명을 다음과 같이 보완했다.

- 작업 유형의 CONFIRMED는 고객이 요청한 작업 종류의 확인이며 고장 원인·시공 가능성의 확정이
  아니라는 의미를 명시했다. 명시적인 수리·교체 요청의 출력 예시를 추가했다.
- 증상 추출과 의도·작업 유형 분류를 별도로 수행하고 명시된 증상을 누락하지 않도록 했다.
- observedText는 원문을 그대로 복사하고, unsure는 고객이 모른다고 말한 해당 항목에만 쓰도록 했다.
- 수리·교체 요청 자체와 직접 사람 연결 요청을 구분하고, 현재 fields만 보고 새 관찰을 만들지 않도록 했다.

원문 근거 검사·필수정보 검사·안전 조건·UNCONFIRMED의 예약 차단은 유지했다.
REPAIR라는 후보 값만 있다는 이유로 CONFIRMED로 승격하지 않는 회귀 검사도 추가했다.
공통 추출 프롬프트를 바꿨으므로 최종 검사는 실패 사례만으로 한정하지 않고 14개 전체를 다시 실행했다.

도구의 첫 두 사전 확인 실행은 STS 클라이언트 정리 방식 오류로 추론 전에 중단됐다.
기존 어댑터와 같은 `contextlib.closing`으로 고쳤고 재발 방지 검사도 추가했다.
이 두 실행에서 Bedrock 모델 호출은 없었다. 실패 기록도 삭제하지 않았다.
